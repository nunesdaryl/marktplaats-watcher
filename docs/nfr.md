# Non-functional requirements

Snapshot: **30 September 2026**. These are current limits and measurements, not promises where measurement is missing. The nine questions cover the operating constraints identified by the [FDE audit §3.1](audit/2026-09-29-fde-course-audit.md).

1. **How quickly should chat answer (p95)?** **Not measured yet.** The chat turn deadline is 60 seconds; the Vercel Python function has `maxDuration` 300 seconds. Chat output is capped at 1,500 tokens per model call. Measure p95 from the `ms` field of production `chat_turn` JSON logs over a stated time window and sample size. Sources: [design §18](system-design.html), [runbook logs](../RUNBOOK.md), `main.py`, `agent.py`, `vercel.json`.
2. **How quickly must a check finish?** No measured p95 yet. The check API fetch has a 240-second timeout; AgentMail fetches have a 15-second timeout. The ranker output cap is 2,500 tokens. A timed-out or failed check is retried within 30 minutes; unscored listings are not e-mailed. Sources: `frontend/convex/checker.ts`, `agent.py`, [runbook §5](../RUNBOOK.md).
3. **What is the peak workload?** Peak traffic has **not been measured yet**. Configured bounds are one dispatcher every 15 minutes, at most five watches per user, and at most 20 new listings scored per watch per check. One check may read at most 40 Marktplaats pages. These are limits, not observed demand. Sources: [design §12 and §16](system-design.html), [cost report §4](../evals/report.md), [README limits](../README.md).
4. **What availability do users get?** **Not measured yet**; there is no evidenced availability percentage or SLO. Measure site and API success over time with the 30-minute [uptime workflow](../.github/workflows/uptime.yml), recording failures and the observation window. Source: [runbook monitoring](../RUNBOOK.md).
5. **How are failures seen and recovered?** Checks and chat emit structured logs; request ids link API responses, Vercel logs and Convex errors. The owner gets a daily problem digest; alert e-mail is retried at the next three checks and is reported after four failed attempts. A crashed check is picked up within 30 minutes. Sources: [runbook trace and alerts](../RUNBOOK.md), [design §13](system-design.html).
6. **What does a user cost, and what is the ceiling?** The 30 September measured 20-listing check costs **€0.00511**; one busiest-case 15-minute watch costs **€14.73/month** and exceeds the OpenAI project's **$10/month hard cap**. A chat question costs about **€0.0018**. This is a project cap, not a per-user monetary ceiling; a per-user cost ceiling is **not decided yet**. Hosting on Vercel, Convex, Clerk and AgentMail free tiers has **€0 fixed cost today**. Source: [evaluation report §4](../evals/report.md).
7. **How is usage bounded?** Chat defaults to 40 questions per user per Europe/Amsterdam day, with the owner exempt; since MW-85 (5 Oct) chat fails closed on a Convex usage or admission-check outage (ADR-0012 amendment); only admitted users (the first 100) can use the AI. `CHAT_PAUSED` and `CHECKS_PAUSED` separately stop chat and scheduled checks. Source: [runbook §1](../RUNBOOK.md), [README limits](../README.md).
8. **Who may read or change data?** Clerk verifies chat sessions; watch writes require the user's own login and confirmation, while owner dashboard access needs both `OWNER_CLERK_ID` and `OWNER_EMAIL`. The Python-to-Convex routes use `API_TO_CONVEX_SECRET` in `X-Api-Secret`. CSP is report-only pending a clean sign-in check. Sources: [design §12–13](system-design.html), [runbook §7 and §9](../RUNBOOK.md), [deployment guide §2](../DEPLOY-VERCEL.md).
9. **How long is data kept?** Untouched chats, seen listings and alerts are purged after 30 days; ratings after 12 months since their last update; errors after 30 days; usage events after 90 days. Saved watches persist until the user deletes them. **Delete my data** removes the app records; the Clerk account is managed separately. Sources: `frontend/convex/checker.ts`, `frontend/convex/crons.ts`, [runbook §8](../RUNBOOK.md).
